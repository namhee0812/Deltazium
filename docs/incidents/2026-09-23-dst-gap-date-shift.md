# 2026-09-23 — DST 공백 시각의 DATE가 1시간 밀려 적재 (Connect JVM 타임존)

## 요약

prefix 정리 후 Oracle 4개 테이블을 재스냅샷하고 정합 검증을 돌리자 `CDC.NH_CDC_TEST_5`
(206컬럼, 466,025행)가 **행수 일치·체크섬 불일치**로 나왔다. 외부 쓰기가 전혀 없는
상태라 파이프라인 내부 변환이 원인일 수밖에 없었고, 컬럼별 해시합 비교로 `RGST_DT`(DATE)
1개 컬럼, 행 단위 diff로 **466,025행 중 1행**을 특정했다:

```
소스  KIGGERAL|7  RGST_DT = 1951-05-06 00:46:18
타깃  KIGGERAL|7  RGST_DT = 1951-05-06 01:46:18   (+1h)
```

## 원인

한국은 1951-05-06 00:00 KST에 서머타임을 시작해 시계를 01:00 KDT로 옮겼다(`zdump -v
Asia/Seoul`). 즉 **1951-05-06 00:00~00:59:59는 Asia/Seoul에 존재하지 않는 로컬 시각**이다.
소스 Oracle `DATE`는 시간대 없는 값이라 그대로 저장돼 있지만, Connect 워커 JVM이 시스템
타임존(Asia/Seoul)으로 돌고 있어 Oracle JDBC가 `DATE`→`java.sql.Timestamp`로 꺼내는 지점에서
JVM 로컬 캘린더가 개입했고, 존재하지 않는 시각이 1시간 뒤로 정규화된 채 epoch로 변환돼
sink까지 갔다. 랜덤 생성 테스트 데이터가 우연히 공백 구간(1948–51·55–60·87–88년 전환 시각)에
하나 걸린 것이다.

부수 확인: 옛 정합 검증(`TO_CHAR(컬럼)` 기본 NLS 포맷 = 날짜만)이었다면 시각 차이를 못 보고
"일치"로 나왔을 것이다. 같은 날 교체한 컬럼별 `ORA_HASH` 방식이 이 차이를 잡았다.

## 조치 (2026-09-23)

- `deploy/start-infra.sh`: Connect 워커 기동에 `KAFKA_OPTS=-Duser.timezone=UTC`. UTC엔 DST
  공백이 없어 시간대 없는 값의 왕복이 항등이 된다. 워커가 여러 대면 전부 같은 값이어야
  하고, Connect 로그 시각은 UTC로 찍힌다. backend·recovery-job·UI는 epoch(`ts_ms`·`_pos`)를
  쓰므로 영향 없음.
- 어긋난 1행은 소스에서 no-op UPDATE(`RGST_DT = RGST_DT`)로 변경 이벤트를 1건 만들어
  재적재 → 타깃 00:46:18로 정정, 정합 검증 일치.
- 재현 검증: `CDC.NH_MIX_TABLE_02`에 공백 시각 2행 INSERT(`ZZ1/195105` 1951-05-06 00:30,
  `ZZ2/198805` 1988-05-08 02:30, DATE·TIMESTAMP 둘 다) → UTC 워커에서 타깃에 소스와 동일하게
  도착. 이 2행은 테스트 데이터로 남겨 두었다.

## 교훈

- 시간대 없는 타입(DATE·TIMESTAMP)은 파이프라인 어디서도 "어느 지역의 로컬 시각"으로
  해석돼선 안 된다. JVM 기본 타임존이 로컬이면 드라이버 수준에서 그 해석이 끼어든다 —
  베어메탈에서 시스템 TZ를 물려받는 구성이 예외였고, 컨테이너(UTC 기본)로 가면 자연히
  해소되지만 명시하는 편이 안전하다.
- 정합 검증은 값의 전체 정밀도를 봐야 한다. 문자열 정규화 방식은 포맷에 따라 정보를
  잃는다(DATE의 시각 부분).
- 46만 행 중 1행 차이는 행수·샘플 조회로는 절대 안 보인다. 체크섬이 "다르다"고 할 때
  컬럼별→행별로 좁히는 절차(sqlplus 덤프 + diff)를 operations.md에 남길 가치가 있다.
